Issue #223

Reversible Promotion and the Seven-Day Initial Lease

Archived memories cannot be manually recalled to working tier, and new memories decay too quickly. This design restores promotion from archival and establishes a seven-day grace period for new nodes by wiring the configured initial stability to both creation and promotion.

The Problem

Three independent gaps block recall and reintroduction of archived nodes:

  1. Archival is one-way. TierManager.promote() exists but has no production caller; enforce_core_cap is the only call site. A deliberately recalled node cannot return to whisper-eligible working tier.
  2. New nodes ignore configured stability. fsrs_initial_stability is validated but never passed to remember(), so new nodes take the model default S = 1.0. At the default fsrs_decay_threshold = 0.3, this reaches decay threshold after ~28.9 hours — a new memory becomes a decay candidate on its second day.
  3. The consolidation exclusion is too broad. Blanket exclusion of every derived_from target blocks promotion of unrelated linked nodes. Only consolidation sources that were actually superseded should be excluded.

The Decision

From issue #191 (closed design decision):

Initial stability floor: −7 / ln(0.3) = 5.814 — a mathematically derived value that gives a seven-day unused working window. This becomes both the default for fsrs_initial_stability and the floor for promotion.

Promotion path: Archival → working on confirmed use from recall_node or source-qualified positive feedback, with bounded reinforcement applied first, then the floor.

Provenance: Record explicit consolidation/supersession; block automatic promotion only for those sources. Generic derived_from relationships do not block promotion.

Execution Order Matters

When a node is confirmed used from archival:

  1. Apply bounded reinforcement using old stability: 1 → 2.0
  2. Apply promotion floor: 2.0 → 5.814
  3. Flip tier: archival → working

This is one atomic lifecycle operation. Inverting the order or applying the floor to the bounded result would grant longer than one initial lease — the max is what keeps it structural rather than incidental.

Changes Across Seven Modules

1. src/ormah/config.py

Change default: fsrs_initial_stability: 1.0 → 5.814. Record the derivation −7 / ln(0.3) in the line comment. Existing validators already cover it; no new logic needed.

2. src/ormah/lifecycle.py

One new pure function (no I/O, no settings, no database): 

def promotion_floor(stability: float, initial_stability: float) -> float:
    """``max(S, initial)`` — the lease a promoted node restarts from."""

Uses max, never a sum. This keeps the idempotence structural: repeated promotions cannot amplify the same event into a longer-than-initial lease.

3. src/ormah/models/node.py

Add field: superseded_by: str | None = None — the id of the consolidation node that replaced this one. Deliberately not exposed in UpdateNodeRequest; this is policy state written only by consolidation.

4. src/ormah/store/markdown.py

Serialize only when not None (following the existing optional-field pattern). Parse via meta.get("superseded_by").

5. src/ormah/index/schema.sql and src/ormah/index/db.py

Add column: superseded_by TEXT on nodes table. Add one entry to the _migrate pair list in db.py. PRAGMA table_info-guarded, so it is idempotent and existing rows stay NULL.

6. src/ormah/engine/memory_engine.py — The Core Logic

The promotion lives inside _record_confirmed_use, after the bounded reinforcement cooldown block: 

if node.tier is Tier.archival and node.superseded_by is None:
    node.stability = lifecycle.promotion_floor(
        node.stability, self.settings.fsrs_initial_stability
    )
    self.tier_manager.promote(node, Tier.working)

Three sub-decisions embedded here:

Why the floor runs even under cooldown

Otherwise a second confirmed use on the same day promotes with old S = 1, buying a ~29-hour lease, and the next decay run demotes straight back. The floor is max against a constant, so running on every promotion cannot push past one initial lease.

Why TierManager.promote(), not direct assignment

This gives the root cause its first production caller and brings the tier-ordering guard along. promote() calls touch_updated(), so updated advances — this is correct, as the tier genuinely changed, and updated feeds LWW sync. Not advancing it would let stale remote copies win.

No archived_at handling

Verified on the island: archived_at appears nowhere in src/ or tests/, is absent from schema.sql, and background/forgetting_manager.py does not exist. All of that is issue #28, which is local-only work on local-main, not in upstream/main. There is nothing to extract into a shared helper.

The UPDATE statement gains two columns (no branching logic): 

UPDATE nodes SET access_count=?, last_accessed=?, stability=?,
                 last_review=?, tier=?, updated=? WHERE id=?

On non-promoting paths, both values are already on disk. When a promotion happens, one _write_audit_log(operation="promote", ...) runs after the transaction closes.

Also in this module: _mark_superseded(source_id, consolidation_id), a serialized operation that sets the field on the loaded node, saves markdown, and writes the column in one transaction. This is needed because the field deliberately does not travel through update_node.

7. src/ormah/background/consolidator.py

Mark superseded_by before demoting in the derived_from + demote loop. The order is the fail-safe: crashing between the two leaves the node working + marked (harmless, since the marker only blocks automatic promotion). The reverse order would leave it archival + unmarked — exactly the promotable node we do not want. derived_from is untouched, giving "a generic derived_from target can promote" for free.

What Deliberately Stays Unchanged

Three independent 1.0 defaults remain in place:

  • MemoryNode.stability's Field(default=1.0)
  • parse_node's meta.get("stability", 1.0) fallback
  • stability REAL DEFAULT 1.0 in schema.sql

Changing any would retroactively rescale nodes that never carried the field, which issue #191 forbids. Only remember() gains stability=self.settings.fsrs_initial_stability.

lifecycle_model_version stays at 2. Nothing reads it on the promotion path and no existing data is rewritten. The version records which reinforcement model wrote this store, and #223 does not change the reinforcement model — it changes a creation default and adds a column. Recorded as a deliberate decision, not an omission, with a test pinning the value.

Concurrency and Failure

run_decay holds _memory_operation_lock for its whole run, and _record_confirmed_use takes the same RLock. Verified: decay and promotion cannot interleave in-process. Decay takes its tier='working' snapshot under the lock, so it cannot see a node promoted after it; and a node promoted before the snapshot appears with last_accessed = now, so R ≈ 1 and decay skips it.

That guarantee is inherited, not built here — and it is under review. Issue #240 documents the lock as a starvation defect, and its proposed fix is precisely to stop background jobs from excluding the foreground. This coupling is visible to whoever lands either change.

What breaks if the lock stops excluding: run_decay reads its snapshot outside any transaction and demotes row by row afterwards. A node whose confirmed use lands between the snapshot and its own demotion would be archived on stale data — losing the seven-day lease. Today the lock makes that interleaving impossible. If #240 lands a fix that removes whole-run exclusion, the promotion will need a revalidation inside the demoting write (demote only if last_accessed still matches the snapshot).

Further Limitations (Pre-Existing)

  • No cross-process exclusion. A CLI running alongside the server does not share the RLock. The guarantee holds inside the server process where both paths live (scheduler thread + request thread).
  • A window between file and index. If file_store.save succeeds and the UPDATE fails, markdown says working while the index says archival. Markdown is the source of truth and the index_updater job reconciles by file_hash every 1 minute; in that window the node is merely not whisper-eligible. This is existing behaviour of every field the method already writes.

Acceptance Criteria → Tests

No new qualification logic. _claim_confirmed_use already fail-closes on signal == 1, source ∈ _CONFIRMED_USE_SOURCES, was_injected == 1, and at-most-once — and all three callers pass through it. Promotion placed inside _record_confirmed_use inherits "unqualified sources do not promote" for free.

Two Consequences This Creates

These did not exist before and are recorded here rather than fixed:

  1. #218's interim rule becomes costlier. Excluding auto_heuristic wholesale used to cost only lost reinforcement. Under #223 a verbatim node_id/title/sentence match on an archival node also becomes a lost promotion. The dossier records 45 such matches, but that is a dossier record (not a measurement in this session) and must be re-measured before use as evidence.
  2. #192 plus supersession is permanent burial. Archival nodes now return on confirmed use — except those marked superseded_by, which are exactly the sources #192 says were harmed. #223 does not regress #192, but it withholds from those nodes the escape it grants everything else. The only way out is manual update_node(tier=working). This is accepted under the #191 ruling (supersession blocks automatic promotion).

Both should be posted as comments on #218 and #192 — GitHub is the durable destination.

Landmine When This Reaches local-main

local-main does have archived_at and forgetting_manager (issue #28); the island does not. The promotion written for upstream is incomplete there: a node promoted out of archival on local-main keeps its archived_at timestamp, leaving a stale graveyard clock on an active node.

When cherry-picking #223 onto local-main, the promotion must additionally clear archived_at on the node and in the index UPDATE. This is deliberately not in the PR — the column does not exist upstream — and it must not be forgotten locally.

Out of Scope

Three related issues are either unblocked or deliberately deferred:

  • Issue #209 (unbounded merge-proposal queue) is unblocked by #223 and needs nothing extra from it. The dossier restricts duplicate candidates to active memories "provided promoted memories become eligible again" — the tier flip in the index is what #209 will query.
  • start_watcher has no production caller and is already documented as deliberate in the storage layer docs. Not touched.
  • Issue #218 (strength calibration) is unchanged by #223, which consumes the interim source-qualified rule.
