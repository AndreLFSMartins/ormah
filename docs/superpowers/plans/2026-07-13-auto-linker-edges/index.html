auto_linker edge-write hardening

For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

Stop auto_linker from aborting an entire run (and freezing its watermark) on a UNIQUE constraint failed: edges collision, close the concurrency hole that triggers the collision, and stop the index rebuild from wiping the reason of every edge.

Overview

Architecture

Three independent concerns, three PRs against upstream/main, plus a landing task that carries the fix into the live Beta. PR A makes the edge write idempotent and a single bad pair non-fatal (fixes issue #117). PR B closes the manual-trigger concurrency hole in the admin routes (what triggered the observed collision). PR C makes reason survive a reindex, which today it cannot, because the markdown Connection model has no reason field at all.

Tech Stack: Python 3.11+, SQLite, FastAPI, pytest (asyncio_mode=auto), APScheduler 3.11.

Background — diagnosed 2026-07-13

auto_linker failed on every long run with:

WARNING: Auto-linker failed: UNIQUE constraint failed: edges.source_id, edges.target_id, edges.edge_type

Root cause is a check-then-insert race. The "does this edge exist?" guard runs at collection time; the INSERT runs at apply time, after the LLM judgment call. Any concurrent edge writer in that window creates the row first, and the raw INSERT explodes.

Two amplifiers turn one collision into a total run failure:

  1. The edge INSERT shares a transaction with INSERT OR IGNORE INTO auto_link_checked, so the rollback also erases the "checked" marker — the poisoned pair returns on every future run.
  2. Nothing catches the exception at the call site, so the IntegrityError reaches the top-level except, aborts the run, and the watermark never advances. On the live store this froze the cursor at seq 333726 with a ~13k backlog.

Ruled out with evidence: intra-run duplication and the LLM echoing bad IDs.

Verified facts (do not re-litigate)

All three bugs exist on upstream/main. The Beta differs substantially in these files but the fixes apply verbatim to both.

PR A — Idempotent edge writes (closes #117)

Branch: fix/117-auto-linker-idempotent-edges off upstream/main

Task 1: _apply_edge becomes idempotent

An edge that already exists is not an error — someone else created the same link while we were waiting on the LLM. Ignore it and let the auto_link_checked marker commit, so the pair is never re-judged.

The markdown append must become idempotent, NOT conditional on winning the race. The markdown file is the source of truth — reindexing deletes a node's edges and recreates them from the file. If the winner committed the DB row but failed to save its markdown, the edge exists only in the index. If we then skip our own markdown append because we "lost", the next reindex deletes the edge — while auto_link_checked stops the pair from ever being reconsidered. The link is gone forever.

So: always ensure the connection is in the file, adding it only if it is not already there. That is idempotent and self-healing.

Files

  • Modify: src/ormah/background/auto_linker.py:285-312
  • Test: tests/test_background/test_auto_linker.py

Task 2: one bad pair must not abort the run

_apply_edge can still raise (e.g. foreign-key violation). That reaches the top-level except and kills the run, freezing the watermark for the whole store. Catch it at the call site, log which pair, and fail closed on that node.

Task 3: same raw INSERT in conflict_detector

conflict_detector writes contradicts/evolved_from edges with the same unguarded INSERT, and it runs concurrently with auto_linker. Same latent bug, same fix.

PR B — Admin triggers must not start a job that is already running

Branch: fix/admin-task-run-concurrency off upstream/main (independent of PR A)

Why: POST /admin/tasks/{task_id}/run calls runner(engine) directly, bypassing the scheduler. A manual trigger started a second auto_linker while the scheduled one was running; both read the same frozen watermark and raced each other's edge writes. The route also returns {"status": "completed"} unconditionally — it reported success for the run that had just failed, which is how the outage stayed invisible.

Do NOT add max_instances=1 to the scheduler. Verified: it is already the APScheduler 3.11 default. The scheduler was never the problem. The only concurrency hole is POST /admin/tasks/{id}/run.

Task 4: JobTracker knows which jobs are in flight

The routes need to ask "is this job running right now?". JobTracker already wraps every scheduled job and is already on app.state.job_tracker, so it is the natural place — but it only records outcomes, never in-flight state.

Task 4b: runners must stop swallowing their own failures

run_auto_linker and run_conflict_detection catch everything, log, and return None. A route inspecting the return value sees success for a run that just died.

Task 5: admin routes refuse a duplicate run

PR C — reason survives a reindex

Branch: fix/edge-reason-survives-reindex off upstream/main (independent of PR A and B)

The finding: on the live store, 100% of 27,507 edges have reason = NULL — including types only auto_linker and conflict_detector can create. So reasons are being written and then erased.

Why an SQL fix cannot work: The markdown file is the source of truth. Connection has only target, edge, weight — no reason field. Reindexing deletes a node's edges and recreates them from markdown, so reason is structurally unrecoverable. The index updater runs every minute. Any reason therefore has a lifetime of at most ~60 seconds.

The fix is to make reason part of the file format. edges.reason already exists in the schema — no DB migration is needed.
