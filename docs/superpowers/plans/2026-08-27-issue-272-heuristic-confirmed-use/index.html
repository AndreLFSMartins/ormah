Heuristic Confirmed Use Implementation Plan

Overview

Let a heuristic whisper reference reinforce a memory when its evidence is verbatim, so the detector carrying 81% of positive volume stops being a lifecycle dead end.

The heuristic commit block wrote a signal and an affinity row and stopped—0 of 1,629 positive heuristic pairs ever took a claim. This plan gates the claim on an evidence floor of 0.80 (the implicit rung of the signal-strength ladder), admits auto_heuristic above that threshold, re-anchors the judge's suppression on confirmation rather than any reference, backfills historical rows, and makes the reinforcement durable across transient failures.

Architecture

_claim_confirmed_use admits auto_heuristic gated on an evidence floor of 0.80 — the implicit rung of the #218 ordinal ladder. Verbatim matches (node_id 0.98, title 0.94, sentence 0.92) clear it; token_overlap cannot, its band's supremum being 0.78. The judge's suppression is re-anchored on confirmation rather than any reference, so weak hits keep the only route that can still confirm them. A boot migration backfills rows the defect already wrote.

Tech Stack

Python 3.11+, SQLite, pytest (asyncio_mode = auto), ruff (line-length 100).

Task 1: The Evidence Floor in _claim_confirmed_use

Depends on Task 0

Background

_CONFIRMED_USE_SOURCES omitted auto_heuristic deliberately—the #220 design conditioned admission on "#218 providing signal calibration". #218 has landed that calibration, so admission is now correct, but only above a floor. Without the floor, token_overlap (97.4% of heuristic hits, and the least precise kind) would gain the same lifecycle power as a verbatim node_id match.

Why contract 9 still passes

test_auto_heuristic_positive_does_not_confirm calls submit_feedback(..., source="auto_heuristic"), whose strength comes from signal_strength.feedback_strength, and _FEEDBACK_LADDER maps auto_heuristic to UNKNOWN (0.40)—below the floor, always. The test keeps passing without a special case. Only its docstring is stale.

Add the constant and admit the source in src/ormah/engine/memory_engine.py:
HEURISTIC_CONFIRM_FLOOR = signal_strength.IMPLICIT

_CONFIRMED_USE_SOURCES = frozenset({"explicit", "implicit", "auto_llm_judge", "auto_heuristic"})

Gate the claim with the floor on auto_heuristic only—explicit (1.00) and the judge (≥0.82) clear it anyway, and applying it to them would add a second gate on paths that do not need one.

Task 2: The Heuristic Block Claims and Reinforces

Depends on Task 1

Background

The heuristic commit block wrote a signal and an affinity row, then stopped. This is the change the issue is about: 0 of 1,629 positive heuristic pairs ever took a claim.

The affinity row this block writes is settled in Task 3

This block writes _insert_affinity(signal=1, ...) for every positive hit—the floor gates the claim, not the affinity row—so a token_overlap hit still records a +1 here. That is deliberate and unchanged. It only becomes a problem once Task 3 starts sending those weak hits to the judge.

Insert the claim inside the heuristic transaction, after _insert_affinity and before the early return at if not llm_groups:. Reinforce in its own post-commit loop, isolated per node.

The judge's loop lives at line 623, but the early return at 531 means the judge's loop never runs when there is nothing to judge—which, since a confirming heuristic hit now suppresses the judge, is exactly the case this loop exists for.

Task 3: Re-anchor the Judge's Suppression on Confirmation

Depends on Task 2

The problem

Line 505 reads: if llm_judge_enabled and not has_llm_judge and not referenced:

not referenced means any heuristic hit suppresses the judge—including a weak token_overlap hit that, after Task 1, confirms nothing. That hit is then left with no confirmation route at all: too weak to claim, and denied the one detector that could still judge it. That is 1,587 of the 1,629 rows.

The condition should be "this event is already settled", not "the heuristic saw something".

Why confirmed_use_claims, not just the strength

  • First pass: the strength is in hand from _node_usage_evidence, and the claim has not been taken yet.
  • Re-ingest: the strength is not in scope at all. The row query returns only heuristic_polarity.
  • MCP feedback: a positive submit_feedback submitted through MCP. has_llm_judge is structurally blind to that.
The regression this task creates and must therefore close: Sending weak hits to the judge is the point of this task—and it also makes a latent contradiction reachable for the first time. Task 2 writes _insert_affinity(signal=1) for every positive hit, token_overlap included. affinity carries a unique index and _insert_affinity uses ON CONFLICT DO NOTHING, so if the judge answers irrelevant for that same event, its -1 row is silently discarded. Task 3 Step 5 closes this by letting the judge overwrite an auto_heuristic affinity row.

Task 4: Backfill the Rows the Defect Already Wrote

Depends on Task 1 · May run in parallel with Tasks 2 and 3

Background

The defect already ran in production. Tasks 1–3 fix future whispers; the exact-match rows already in signals would stay unclaimed forever, because the gate runs at write time. Expected volume on the measured store (2026-08-26): 42 pairs—29 node_id, 13 sentence, 0 title—out of 1,629. The 1,587 token_overlap rows are correctly left alone.

Two rules this migration must not break

  1. Eligibility is recomputed from evidence, never read from signals.strength. That column defaults to 1.0—above the floor—so trusting it would confirm every stale positive heuristic row, including the 1,587 token_overlap ones. Use signal_strength.strength_from_evidence(source, polarity, evidence), which is a pure function and fail-closed (unknown match → 0.40; polarity 0 → 0.0).
  2. Reinforcement runs after the transaction commits. _record_confirmed_use does file I/O; calling it inside would take db_lock before memory_lock (#220 §4.3).

Why a rescan, not a one-time stamp

A one-time stamp cannot repair what an OLD binary writes AFTER the stamp is set—a rollback then re-upgrade, or the second unmanaged server process of #238. Those rows would stay unclaimed forever.

Add _migrate_heuristic_confirmed_use() method after _migrate_signal_strength ends, and call it at boot in startup(), immediately after the ladder migration—as defence in depth, not as the safety mechanism.

Task 5: Durable Reinforcement After the Claim (#220 debt)

Depends on Tasks 2, 3, and 4

Background

_claim_confirmed_use takes the at-most-once latch inside the caller's transaction; that transaction commits; only afterwards does _record_confirmed_use run, exception isolated. The claim is a monotonic latch with no undo, so nothing retries. One transient filesystem failure defeats the reinforcement permanently for that node.

The defect predates #272—it arrived with the #220 lifecycle family. Task 5 makes the promise durable by adding a state column to track the claim's outcome and a reinforcement_retry sweeper to repair claims left unapplied.

Council round 1 refuted the earlier atomic framing (run 98918652-c2f6a005-fc06a07a). os.replace is irreversible and COMMIT runs after the body, so a failed commit leaves the markdown advanced while the row rolls back. No ordering can enrol a filesystem in a SQLite transaction. What makes it safe is where the new values come from: two sources, both pinned.

This is convergence, not atomicity

  • The counters come from the nodes row, read inside the transaction, instead of from the markdown. access_count is therefore row["access_count"] + 1 on every attempt, so a retry recomputes the same target and overwrites the phantom instead of compounding it.
  • The clock comes from the claim's claimed_at, never from datetime.now(). Council round 1 (Cursor, MEDIUM) caught that the counter alone is not enough: stability, last_review and last_accessed are all functions of when the write runs. Sourcing the clock from claimed_at makes the whole target a pure function of the claim. A late retry stamping datetime.now() would also credit the memory with recency it never earned—the use happened at claimed_at; that is what gets recorded.

Schema changes

confirmed_use_claims gains three columns:

Column Meaning
state pending (sweeper retries), applied (done), legacy_unknown (pre-#272), orphaned (node gone)
reinforced_at When the write landed (separate from claimed_at, which is when the use happened)
last_attempt_at When the sweeper last tried this claim; ineligible until backoff expires
The DEFAULT is terminal, deliberately. A pre-#272 binary inserts without naming state, so it takes the column default. That binary's mutator never marks anything applied, so a 'pending' default would leave the row eligible forever and the sweeper would re-reinforce it every hour, compounding the reinforcement the old binary already performed. Two binaries on one store is not hypothetical—see issue #238 in CLAUDE.md. Only the new code inserts 'pending' explicitly.

Why last_attempt_at stops batch starvation

With ORDER BY claimed_at ASC LIMIT N and no record of attempts, N permanently-failing claims fill every batch forever and a claim taken today is never tried at all—the sweeper reports itself healthy while the feature is dead for every new claim. An attempted row steps out of the eligible set until the backoff expires, so the next run reaches past the wall.

The reinforcement_retry sweeper

Runs as a sleep-cycle job, selecting pending claims past a 5-minute grace margin. Stamps last_attempt_at before the loop (committed separately) so attempted rows step out until backoff expires. Isolated per node so one failure does not abandon the batch. Logs the repair rate.

Create src/ormah/background/reinforcement_retry.py with the sweeper function and batch/backoff constants. Register it in the scheduler, config settings, and admin routes.

Why the 5-minute grace margin

A claim taken seconds ago may still have its reinforcement in flight—the mutator runs after the claiming transaction commits. Matches the interval session_watcher_reconcile_interval_minutes uses for the same reason.
