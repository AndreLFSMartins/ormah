Task 1: The Evidence Floor in _claim_confirmed_use

Background

_CONFIRMED_USE_SOURCES omitted auto_heuristic pending #218 signal calibration, which has landed. Admission is now correct, but only above a floor. Without the floor, token_overlap (97.4% of heuristic hits) would gain the same lifecycle power as a verbatim node_id match.

Why contract 9 still passes

Task 2: The Heuristic Block Claims and Reinforces

Background

The heuristic commit block writes signal and affinity, then stops: 0 of 1,629 positive heuristic pairs ever took a claim.

Two ordering rules — both load-bearing

  1. _insert_affinity runs BEFORE the claim. Helper reads changes(), nothing may sit between INSERT and read.
  2. Reinforcement runs AFTER transaction closes. _record_confirmed_use does file I/O; calling it inside inverts lock order.

Why its OWN reinforcement loop

The judge's loop at :623 sits after :531 early return. After Task 3, a confirming heuristic hit produces no llm_groups — reusing that loop would skip reinforcement precisely when it matters. The new loop must sit between the heuristic transaction and the early return.

Summary

Inside transaction, after affinity, take claim for positive hits. After transaction, before early return, reinforce in isolated loop. Rewrite contract 12: the floor, not the source, is the gate.

Task 3: Re-anchor the Judge's Suppression on Confirmation

Background

not referenced suppresses judge for ANY heuristic hit — including weak token_overlap that confirms nothing. That hit has no route left: too weak to claim, denied the judge. That is 1,587 of 1,629 rows.

Condition should be "event already settled", not "heuristic saw something".

The regression this task creates

Sending weak hits to judge makes a latent contradiction reachable. Task 2 writes _insert_affinity(signal=1) for EVERY positive hit. affinity is unique per (node, event), uses ON CONFLICT DO NOTHING. If judge answers irrelevant, its -1 is silently discarded — signals records negative verdict, retrieval keeps consuming the +1.

Task 3 closes this: scoped UPDATE lets judge outrank heuristic affinity, following _submit_feedback_locked pattern.

Judge preamble is mandatory

Judge doesn't run unless both flags on. Every test must carry:

Summary

Add already_confirmed to row query via EXISTS subquery. Re-anchor suppression on settled = confirms or bool(row["already_confirmed"]). Judge verdict overwrites only heuristic affinity. Import floor from memory_engine.

Task 4: Backfill the Rows the Defect Already Wrote

Background

Defect already ran in production. Tasks 1–3 fix future whispers; exact-match rows already in signals stay unclaimed forever (gate runs at write time). Expected volume 2026-08-26: 42 pairs (29 node_id, 13 sentence, 0 title) of 1,629. The 1,587 token_overlap rows correct skipped.

Two rules this migration must not break

  1. Recompute from evidence, never read signals.strength. Column defaults 1.0 (above floor), so pre-ladder rows read as confirmable. Second process writes stale rows in window between ladder and backfill commits. Recomputing makes column irrelevant.
  2. Reinforcement runs after transaction commits. File I/O inverts lock order.

Why rescan, not one-time stamp

Old binary writes pre-fix rows AFTER stamp is set (rollback, re-upgrade, or #238's second process). Stamp calls them migrated forever.

Summary

Add version constant. Write _migrate_heuristic_confirmed_use that rescans rows above cutoff, recomputes strength from evidence in Python, applies every eligibility test in Python, reinforces eligible rows in isolated loop. Call at boot after ladder as defence-in-depth.

Task 5: Durable Reinforcement After the Claim (#220 debt)

Background

Claim takes inside caller's transaction; transaction commits; only then _record_confirmed_use runs, wrapped in bare except that logs and swallows. Claim has no undo, nothing retries. One transient filesystem failure defeats reinforcement permanently.

Defect predates #272 (#220 family). #272 raises stakes: Task 4's backfill runs batch at once.

This is convergence, not atomicity

os.replace is irreversible, Database.transaction issues COMMIT after body returns. Failing COMMIT leaves markdown advanced, row and claim rolled back. No ordering enrolls filesystem in SQLite transaction.

What makes it safe: where new values come from — two sources pinned:

  1. Counters from nodes row, not markdown increment. access_count = row["access_count"] + 1 on every attempt, retry recomputes same target, overwrites phantom instead of compounding.
  2. Clock from claim's claimed_at, not datetime.now(). Retry stamping wall-clock feeds different days_since, lands on different FSRS value. Reading from claimed_at makes target pure function of claim.

Point 2 fixes truthfulness bug: last_accessed is decay anchor. Late retry stamping now() credits recency never earned. Use happened at claimed_at; that's what gets recorded.

Why this task may reorder mutator, Tasks 1–4 may not

FileStore built with engine's _memory_operation_lock, an RLock that @_serialized_memory_operation already holds. Call from inside method's own transaction re-enters rather than taking db_lock first. Callers unchanged: still invoke outside their transaction.

Summary

Add state, claimed_at, reinforced_at columns with DEFAULT 'legacy_unknown' (terminal). Migration marks pre-existing terminal. Reorder mutator: read row, write file, update database. Create sweeper reinforcement_retry.py rescanning pending claims. Add to scheduler as sleep-cycle job.
