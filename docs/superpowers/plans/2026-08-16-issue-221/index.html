1 The Lifecycle Module

Create the foundational pure module that owns all lifecycle math: retrievability, spacing, reinforced stability, and cooldown detection. This module has no I/O, no database access, and no settings dependency — it is a computational layer that Tasks 3 and 4 call to keep the curve consistent.

Interfaces

  • Consumes: nothing (pure stdlib module).
  • Produces, for Tasks 3 and 4:
    • retrievability(days_since, stability, *, fallback_stability=1.0) -> float
    • spacing_factor(days_since, stability, cap, *, fallback_stability=1.0) -> float
    • reinforced_stability(stability, days_since, *, growth_factor, growth_exponent, spacing_cap, max_stability, initial_stability) -> float
    • reinforcement_due(last_review, now, cooldown_days) -> bool

Rationale

exp(-t/S) is currently written out in three files. A curve change means three edits that can silently diverge. Centralizing the math lets Tasks 3 and 4 stay small and keeps the rebase conflict with #220 (which renames _touch_access) down to a function signature.

3 Cooldown and Bounded Reinforcement

Introduce the per-node, per-day cooldown on numeric stability updates. Every use still advances last_accessed and the decay anchor, but only one reinforcement per cooldown window moves stability. Serialization is mandatory because the cooldown is a check-then-write pair and the recall paths are not themselves serialized.

Interfaces

  • Consumes: ormah.lifecycle.reinforcement_due and ormah.lifecycle.reinforced_stability (Task 1); the four Settings fields from Task 2.
  • Produces: no new public names. _touch_access keeps its signature and its five call sites stay untouched.

Behavior Contract

Every call advances last_accessed and access_count. Only a call that is off cooldown changes stability and last_review.

Note on #220: PR #234 renames this method to _record_confirmed_use and adds its own zero-stability guard. On rebase, keep the new name and this task's body — the guard now lives in lifecycle.py.

TOCTOU Without the Lock (council round 3, I1)

reinforcement_due reads last_review off the in-memory node and the new last_review is written several statements later. The read and the write are not atomic, and the paths that reach _touch_access are not serialized. Two concurrent recalls on the FastAPI threadpool load the same node, both see due=True, and both write a bump.

The fix is the @_serialized_memory_operation decorator: _memory_operation_lock is a threading.RLock (memory_engine.py:93), so it is reentrant — decorating _touch_access cannot deadlock at the call sites that already hold it. It also covers the Markdown write and the DB write as one unit.

Implementation Steps

  3. Add the import from ormah import lifecycle to memory_engine.py.

4 Decay Uses Shared Retrievability; Importance Gets the Anchor Flip
Title corrected in council round 3 (C1). The old title described the rejected first draft. Importance keeps its own recency formula; only the anchor moves. The old Step 7 gate demanded a state that Step 5 forbids; that is fixed too.

Interfaces

  • Consumes: ormah.lifecycle.retrievability (Task 1).
  • Produces: no new names. run_decay(engine) -> None is unchanged.

Three Changes

  1. The inline math.exp(-days_since / stability) in decay_manager becomes lifecycle.retrievability(...) — shared with the reinforcement path (AC5).
  2. The decay anchor flips from last_review or last_accessed to last_accessed or last_review. With the cooldown, last_review can lag the last use by a full cooldown window; anchoring decay on it would let an actively used node look stale.
  3. importance_scorer.py gets the same anchor flip — and nothing else. This file was declared out of scope in the original spec; the council review showed why that was wrong.

Why importance_scorer Is Now In Scope (council finding C2)

The scorer reads its recency anchor as r["last_review"] or r["last_accessed"] with weight 0.33 (config.py:144). The cooldown this issue introduces is precisely what makes last_review lag. A node used today but reinforced yesterday reads as a day old, which costs it importance and can cross the 0.5 gate, demoting the ranking of a memory that is in active use.

The Anchor Flip Is the ONLY Change (council round 2, C2)

The first draft also routed the scorer through lifecycle.retrievability, reading r["stability"]. Both peers rejected that. #222 (PR #235, a merge prerequisite) rewrites the scorer to SELECT id, access_count, last_accessed, importance, last_review FROM nodes — stability is no longer selected. Applying the old draft after #222 lands breaks either way: sqlite3.Row["stability"] raises IndexError (not caught by the surrounding exception), aborting run_importance_scoring for every node; or the hunk undoes #222.

Why Existing Decay Tests Stay Green

_make_stale (test_decay_manager.py:13) backdates last_accessed only, and nodes created by engine.remember have last_review = NULL. Both anchor orders resolve to last_accessed for those rows.

Why Every New Decay Test Sets importance = 0.2 (council finding C1)

run_decay skips a node when importance >= decay_importance_threshold, and both sides default to 0.5 (config.py:155, node.py:58). A decay test that leaves importance at its default never reaches the code it claims to exercise: it passes whether or not the anchor flipped.

5 Integer Lifecycle-Model Version

Replace the boolean fsrs_migrated flag with an integer version that records which model produced the stored stability values. Version 2 marks the bounded-reinforcement model; version 1 is the legacy FSRS seed.

Interfaces

  • Consumes: nothing from earlier tasks.
  • Produces:
    • module-level constant LIFECYCLE_MODEL_VERSION: int = 2 in memory_engine.py
    • MemoryEngine._lifecycle_model_version(self) -> int
    • MemoryEngine._seed_stability_from_access_count(self) -> None
    • _migrate_fsrs(self) -> None keeps its name and its call site at memory_engine.py:151

Semantics

Store state _lifecycle_model_version() Action
No lifecycle_model_version, no fsrs_migrated, no node carries last_review 0 seed from access_count, then write 2 + fsrs_migrated
No lifecycle_model_version, no fsrs_migrated, but some node carries last_review 1 skip the seed, write 2 + fsrs_migrated
No lifecycle_model_version, fsrs_migrated = '1' 1 skip the seed, write 2 + fsrs_migrated
lifecycle_model_version present but unreadable 1 skip the seed (fail closed), rewrite both keys
lifecycle_model_version = 2 2 nothing

Version 2 records which model produced the stored stabilities. It does not rescale them: #191 rules that a future curve migration must preserve each node's archival deadline rather than apply a constant factor.

Downgrade Is Not Supported (council round 3, C2; decision: André, 2026-08-16)

Downgrading below LIFECYCLE_MODEL_VERSION after an upgrade is unsupported. Roll back the binary only together with a backup taken before the upgrade. The version marks which model wrote the stability, and a binary that predates the key keeps writing with the unbounded formula while leaving the version marker at the newer value.

Out of Scope (council round 2, both peers, high)

The last_review guard in _lifecycle_model_version protects exactly one shape of restore: the one where the index is gone, so meta comes back empty. It does nothing for a restore onto an installation whose index is still there. This is a pre-existing defect, not one this issue creates. Fixing it is out of scope and belongs to its own issue — r-spade/ormah#236. Do not claim anywhere in this plan, in the PR body, or in the docs that the C3 guard covers restore in general.
