The problem

Consolidation is lossy when applied iteratively to its own output.

_apply_consolidation creates the consolidated node with tags=["consolidated"] and leaves tier at the CreateNodeRequest default, working. This makes consolidation outputs eligible as consolidation inputs on the next run.

Consolidated nodes are short by construction (3–8 sentences), so they cluster more easily than their sources. When they re-cluster, the new summary is written from two summaries while the real sources sit in archival, no longer read. Each pass is lossy; applied to its own output the loss compounds and cannot be recovered.

Verified by: reading upstream/main:src/ormah/background/consolidator.py (the two SELECT queries) and upstream/main:src/ormah/models/node.py (tier: Tier = Tier.working default).

Decision

A consolidated node is terminal for cluster discovery.

Consolidated nodes will never be a seed and never be a member of a consolidation cluster. A summary is the primary representation of its cluster and is not re-summarised.

Trade-offs accepted

When genuinely new related memories arrive, they form a second summary next to the first instead of updating it. Merging the two is the duplicate_merger's job (human-curated proposals, ADR 0005).

Re-consolidating from the original sources — the semantically ideal behaviour — needs provenance that issue #258 is building and interacts with issue #260's cluster splitting. This is a follow-up, recorded on the issue, not part of this change.

Alternatives rejected

  • Member yes, seed no, at most one per cluster — still rewrites a summary from a summary (S1 → S2 → S3), the same defect at a lower rate.
  • Re-consolidate from sources — right semantics, wrong size for this issue (needs provenance work from #258 first).
  • Document the current behaviour — the short-summary size constraint pushes toward re-clustering, so "summary of summary" would be a frequent accident, not a rare choice.

Implementation

One file: src/ormah/background/consolidator.py, only the _find_consolidation_clusters function.

Exclusion predicate

A module constant holds the predicate, written once and used in both queries:

_NOT_CONSOLIDATED = (
    "NOT EXISTS (SELECT 1 FROM node_tags WHERE node_id = nodes.id AND tag = 'consolidated')"
)

Query updates

  • Seed query: SELECT id, title, content, space FROM nodes WHERE tier = 'working' AND {_NOT_CONSOLIDATED}
  • Member query: SELECT id, title, content, space, tier FROM nodes WHERE id = ? AND {_NOT_CONSOLIDATED} (existing tier != "working" check on fetched row stays)

Scope of change

  • Docstring states that consolidated-tagged nodes are terminal and excluded from discovery as seed and as member
  • node_tags(tag) is already indexed (idx_node_tags_tag, schema.sql)
  • No schema change, no migration, no settings
  • _apply_consolidation, the prompt, run_consolidation, and _consolidate_cluster are untouched — PR #260 (#192) edits those, not discovery, so the two changes do not conflict

Test specification

Tests in tests/test_background/test_consolidator.py. Both must be red on upstream/main. Embeddings are real (fastembed via the engine fixture); identical content yields similarity 1.0, making clustering deterministic.

Unit: discovery never returns a consolidated id

  1. Create two similar raw working nodes and two working nodes with the same content tagged consolidated
  2. Call _find_consolidation_clusters(engine)
  3. Assert no returned cluster contains a consolidated id

Worked example without the fix:

The seed "consolidated A" pulls "consolidated B" (similarity 1.0) and the raw pair into one cluster of 4 — the assertion fails.

With the fix:

One cluster of the two raw nodes only.

End to end: the issue's scenario

  1. Set consolidation_max_cluster_nodes = 2
  2. Create four similar sources
  3. Mock llm_generate to return one fixed summary
  4. Run 1 produces N1 and N2 (both working, identical content)
  5. Run 2 must create no new node; N1 and N2 remain working; no derived_from edge targets N1 or N2

Without the fix:

Run 2 consolidates N1 + N2 into N3 — the summary-of-summaries.

Fixture validation

Before the red phase: engine.remember(..., tags=["consolidated"]) must populate node_tags. If test 1 is green before the fix, this assumption failed and the predicate must read tags another way (the markdown), not the index.

Out of scope

  • Re-consolidation from sources when new related memories arrive (follow-up after #258)
  • Idempotency under retry (#258)
  • The Claude-in-the-loop maintenance route (#259)
  • Anything in _apply_consolidation, the prompt, or the LLM route
