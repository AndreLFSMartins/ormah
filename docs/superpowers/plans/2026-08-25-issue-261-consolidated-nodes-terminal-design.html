Specification for Ormah issue #261

Consolidated nodes are terminal for cluster discovery

1 file changed
3 tests required
2 SQL predicates
Problem

When _apply_consolidation creates a consolidated node, it defaults to the working tier. The consolidation discovery process then treats it like any other working node: it can serve as both a cluster seed and a cluster member. This creates a critical defect.

A consolidated node — a summary of summaries — should never be re-consolidated. Instead, each pass rewrites from the previous summary, compounding loss until the original sources become unrecoverable.

The problem is verified by reading:

  • upstream/main:src/ormah/background/consolidator.py — both discovery SELECTs exclude no consolidated nodes
  • upstream/main:src/ormah/models/node.py — tier: Tier = Tier.working is the default
Decision

A consolidated node is terminal for cluster discovery. It is never selected as a seed and never accepted as a member of a consolidation cluster. A summary becomes the primary representation of its cluster and is not re-summarized.

When genuinely new related memories arrive, they form a second summary next to the first. Merging the two is duplicate_merger's job (human-curated proposals per ADR 0005). Re-consolidating from the original sources — the semantically ideal behaviour — requires provenance tracking (issue #258) and interacts with cluster splitting (#260). That is a follow-up.

Alternatives rejected

  • Member yes, seed no, at most one per cluster — still rewrites a summary from a summary (S1 → S2 → S3), the same defect at lower rate.
  • Re-consolidate from sources — correct semantics, but too large for this issue (depends on #258, overlaps #260).
  • Document the current behaviour — the short-summary size constraint pushes toward re-clustering, so "summary of summary" would be a frequent accident, not a rare choice.
Change

One file: src/ormah/background/consolidator.py. Only the _find_consolidation_clusters function is modified.

Implementation

  1. Add a module-level constant holding the exclusion predicate: 
    _NOT_CONSOLIDATED = (
    "NOT EXISTS (SELECT 1 FROM node_tags "
    "WHERE node_id = nodes.id AND tag = 'consolidated')"
)
  2. Update the seed query to exclude consolidated nodes: 
    SELECT id, title, content, space FROM nodes
WHERE tier = 'working' AND {_NOT_CONSOLIDATED}
  3. Update the member query to exclude consolidated nodes: 
    SELECT id, title, content, space, tier FROM nodes
WHERE id = ? AND {_NOT_CONSOLIDATED}
    The existing tier != "working" check on the fetched row remains in place.
  4. Add a docstring stating that consolidated-tagged nodes are terminal for cluster discovery.
No schema changes, migrations, or settings adjustments are required. The correlated subquery uses node_tags's primary key (node_id, tag), which already exists.

Secondary impact

MemoryEngine.get_maintenance_batches (at memory_engine.py:1820 in the Claude-in-the-loop maintenance phase 1) also calls _find_consolidation_clusters. The consolidation batch offered to the agent will stop containing consolidated nodes — this is intended behaviour, applying the same terminal rule through one implementation.

Composition with PR #260

Verified with gh pr diff 260: PR #260 (from #192) does not edit the two discovery SELECTs, so the changes compose safely. Both PRs insert module-level constants after imports (_CONSOLIDATE_PROMPT there, _NOT_CONSOLIDATED here), so whichever merges second may see a trivial textual conflict — resolve by keeping both constants.

Tests

tests/test_background/test_consolidator.py. All three tests must be red on upstream/main. Embeddings are real (fastembed via the engine fixture); identical content yields similarity 1.0, making clustering deterministic.

1. Discovery never returns a consolidated ID

Unit test. Create two similar raw working nodes and two working nodes with identical content tagged consolidated. Call _find_consolidation_clusters(engine) and assert no returned cluster contains a consolidated ID.

  • Worked example (broken): The seed "consolidated A" pulls "consolidated B" (similarity 1.0) and the raw pair into one cluster of 4 — the assertion fails.
  • With the fix: One cluster of the two raw nodes only.

2. End-to-end: no re-consolidation of summaries

Integration test. Set consolidation_max_cluster_nodes = 2. Create four similar source nodes. Mock llm_generate to return one fixed summary. Run the consolidation twice.

  • Run 1: Produces N1 and N2 (both working, identical content).
  • Run 2 with the fix: Must create no new node (the set of consolidated-tagged ids is unchanged), must not call the LLM again, and N1 and N2 remain working.
  • Without the fix: Run 2 consolidates N1 + N2 into N3, the summary-of-summaries.

Note: A derived_from edge assertion would not work. On upstream/main, #123 deletes that edge on reindex anyway.

3. Seed-side exclusion is independent of member check

Unit test. Added after council review to show that the seed SELECT predicate and member SELECT predicate are both load-bearing. Same setup as test 1 but insert the two consolidated nodes first. Discovery scans in insertion order.

  • Without the seed predicate only: The first summary seeds a cluster and recruits the raw pair — test fails.
  • Without the member predicate only: Tests 1 and 3 both fail.
  • With the fix (both predicates): All three tests pass.
Fixture verification. Before the red run, confirm that engine.remember(..., tags=["consolidated"]) correctly populates node_tags. If test 1 is green before the fix, this assumption has failed and the predicate must read tags another way (e.g. from the markdown), not the index.
