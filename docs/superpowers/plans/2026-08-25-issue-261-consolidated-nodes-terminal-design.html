A consolidated node is never a seed and never a member of a consolidation cluster. Summaries are terminal and are not re-summarised.

The problem ↑

_apply_consolidation leaves consolidated nodes in the working tier and does not exclude them by tag. As a result, a consolidation output is eligible as a consolidation input on the next cycle. Two consolidated siblings are short by design (3–8 sentences), so they cluster more readily than their sources; when they re-cluster, the new summary is written from two summaries while the original sources sit in archival, out of reach.

Each pass is lossy; applied to its own output the loss compounds and cannot be recovered.

Verified Confirmed by reading upstream/main:src/ormah/background/consolidator.py (both SELECT statements) and upstream/main:src/ormah/models/node.py (default tier: Tier = Tier.working).

The decision ↑

A consolidated node is terminal for cluster discovery: it is never a seed and never a member of a consolidation cluster. A summary is the primary representation of its cluster and is not re-summarised.

Consequence accepted ↑

When genuinely new related memories arrive, they form a second summary next to the first instead of updating it. Merging the two is duplicate_merger's job (human-curated proposals, ADR 0005). Re-consolidating from the original sources — the semantically ideal behaviour — needs provenance that issue #258 is building and interacts with issue #260's cluster splitting; it is a follow-up, recorded on the issue, not part of this change.

Alternatives rejected ↑

  • Member yes, seed no, at most one per cluster — still rewrites a summary from a summary (S1 → S2 → S3), the same defect at a lower rate.
  • Re-consolidate from sources — right semantics, wrong size for this issue (needs provenance work from #258; interacts with #260).
  • Document the current behaviour — the short-summary size constraint pushes toward re-clustering, so "summary of summary" would be a frequent accident, not a rare choice.

The implementation ↑

One file: src/ormah/background/consolidator.py, function _find_consolidation_clusters.

Module constant ↑

Define the exclusion predicate once at module level:

_NOT_CONSOLIDATED = (
    "NOT EXISTS (SELECT 1 FROM node_tags WHERE node_id = nodes.id AND tag = 'consolidated')"
)

Query changes ↑

Seed query: append the exclusion to the WHERE clause:

SELECT id, title, content, space FROM nodes WHERE tier = 'working' AND {_NOT_CONSOLIDATED}

Member query: exclude consolidated nodes in the same way:

SELECT id, title, content, space, tier FROM nodes WHERE id = ? AND {_NOT_CONSOLIDATED}

The existing tier != "working" check on the fetched row stays.

Docstring ↑

Add a note that consolidated-tagged nodes are terminal and are excluded from discovery as seed and as member.

Schema & migration ↑

No schema change, no migration, no settings. The correlated probe by node_id is covered by node_tags's primary key (node_id, tag) in schema.sql. _apply_consolidation, the prompt, run_consolidation, and _consolidate_cluster are untouched.

Side effect: maintenance batches ↑

MemoryEngine.get_maintenance_batches (at memory_engine.py:1820, the run_maintenance Claude-in-the-loop phase 1) also calls _find_consolidation_clusters. The consolidation batch offered to the agent stops containing consolidated nodes too. This is intended — the same "terminal" rule, one implementation.

Composition with PR #260 ↑

Both PRs insert module-level constants immediately after imports (_CONSOLIDATE_PROMPT in #260, _NOT_CONSOLIDATED here). Whichever merges second may see a trivial textual conflict — resolve by keeping both. The changes compose: PR #260 does not edit these two SELECT statements.

Test strategy ↑

Both tests live in tests/test_background/test_consolidator.py and must be red on upstream/main before the fix. Embeddings are real (fastembed via the engine fixture); identical content yields similarity 1.0, which makes clustering deterministic.

1. Unit test — discovery never returns a consolidated id ↑

Setup: Create two similar raw working nodes and two working nodes with identical content tagged consolidated.

Action: Call _find_consolidation_clusters(engine).

Assert: No returned cluster contains a consolidated id.

Without the fix: The seed "consolidated A" pulls "consolidated B" (similarity 1.0) and the raw pair into one cluster of 4 — the assertion fails. With the fix: One cluster of the two raw nodes only.

2. End-to-end test — the issue's scenario ↑

Setup: consolidation_max_cluster_nodes = 2, four similar sources, llm_generate mocked to return one fixed summary.

Run 1: Produces N1 and N2 (both working, identical content).

Run 2 assertions:

  • Must create no new node (the set of consolidated-tagged ids is unchanged)
  • Must not call the LLM again
  • N1 and N2 remain working

Without the fix: Run 2 consolidates N1 + N2 into N3 — the summary-of-summaries scenario.

Fixture check first ↑

In the red phase: engine.remember(..., tags=["consolidated"]) must populate node_tags. If test 1 passes before the fix, this assumption failed and the predicate has to read tags another way (e.g., from the node markdown content), not from the index.

Out of scope ↑

  • Re-consolidation from sources when new related memories arrive (follow-up after issue #258)
  • Idempotency under retry (part of issue #258)
  • The Claude-in-the-loop maintenance route (issue #259)
  • Anything in _apply_consolidation, the prompt, or the LLM route
