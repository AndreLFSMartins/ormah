O problema

Decay é uma catraca de mão única. O decay_manager rebaixa nós working estagnados para archival, mas nada nunca os remove — archival só cresce. No store real do André (8.355 nós, 80% archival) esse cemitério:

  • conta no total de nós (a UI do grafo já sofre);
  • é varrido por todo job de background (auto-linker é O(n²) sobre todos os nós);
  • ainda aparece no recall como ruído (só rebaixado via tier_boost_archival = -0.1).

Decay reduz prioridade — não custo nem ruído. Deleção é a única alavanca que encolhe o store.

Encolher n também é multiplicador grátis para o #26 (auto-linker) e o #25 (vector search).

A restrição

Princípio de confiança Deleção nunca depende de um único sinal. Atua só na cauda archival, exige a conjunção de vários sinais independentes, e mantém uma janela de reversibilidade antes de qualquer byte sair do disco. Cada decisão é explicável por nó.

Um falso negativo — deletar algo que depois importava — é irrecuperável. Por isso o desenho inteiro é fail-closed: OFF por padrão, gates conjuntos, e soft-delete antes de purge.

Fluxo do job

Um novo módulo src/ormah/background/forgetting_manager.py → run_forgetting(engine), registrado no scheduler.py com intervalo próprio. Cada run tem duas fases, ambas guardadas pelo master switch — quando deletion_enabled=False o job retorna na hora (no-op).

Fase A Gates → soft-delete (+ cap backstop)
Fase B Hard-purge da janela de retenção

Reusar engine.delete_node no soft-delete mantém um caminho único de deleção (índice + audit + cleanup de auto-link já tratados), então o job novo fica pequeno.

§1 — Gates de elegibilidade (deleta só quando TODOS valem)

Sobre candidatos tier == archival; predicados baratos em SQL, FSRS R calculado em Python (mesma fórmula do decay_manager: R = exp(-days_since / stability)).

#GateCondição
1Só o graveyardtier == archival — nunca working/core
2Staleness sustentadaarchived_at e last_accessed ≤ now − min_archival_days
3Retrievability no chãoR < deletion_retrievability_floor (mais fundo que o threshold de decay)
4Baixa importânciaimportance < decay_importance_threshold (reusa 0.5)
5Nunca útilNOT EXISTS(affinity WHERE node_id=? AND signal>0) — qualquer +feedback ⇒ protegido
6Baixa conectividadedegree ≤ deletion_max_degree e nenhuma edge com weight ≥ strong_edge_weight
7Não-protegidoNão é o self/user node (não há "pin" no schema hoje)

Cada gate sozinho gera falsos positivos; a conjunção só pega peso-morto genuíno: archival, sem importância, sem uso, nunca útil, fracamente conectado, antigo.

§3 — Forget-score (cap backstop)

Quando archival_soft_cap > 0 e excedido, evicta worst-first por um score composto:

score = (1 − R) · (1 − importance) · age_days · 1/(1 + degree) · no_positive_feedback

age_days = now − archived_at
no_positive_feedback ∈ {0, 1}   # nó com +feedback pontua 0 → nunca evicta

Ordena descendente, evicta até o cap, pulando todo nó protegido sob §1. Se sobrarem só protegidos, o store fica acima do cap — melhor exceder que deletar algo valioso.

Schema & file_store

Migração (uma)

Adiciona nodes.archived_at TEXT (nullable): setada quando um nó é rebaixado para archival (no caminho do decay_manager). A migração em Database._migrate backfilla os archival existentes com o updated atual.

Mudanças no file_store

  • soft_delete(node_id) — estampa deleted_at: <iso> no frontmatter ao mover para deleted/. Centralizado lá, então a deleção manual também ganha janela de reversibilidade.
  • list_deleted() — novo: enumera os arquivos em deleted/.
  • purge(node_id) — novo: hard-remove um arquivo de deleted/.

Operação

Ativar sem UI Adicione ORMAH_DELETION_ENABLED=true (e overrides de tuning) em ~/.config/ormah/.env, depois reinicie o server. A UI web lenta nunca está no caminho crítico.

Testes (TDD)

  • Por gate, positivo + negativo: stale-o-bastante vs recente (archived_at, last_accessed), R abaixo vs acima do floor, importância, +affinity presente (protege) vs ausente, degree/strong-edge, self node pulado.
  • Conjunção: nó falhando exatamente um gate não deleta; passando todos é soft-deletado.
  • Master switch: deletion_enabled=False ⇒ zero deleções, mesmo com elegíveis.
  • soft_delete estampa deleted_at no frontmatter; arquivo cai em deleted/.
  • Purge (Fase B): arquivos além de retention_days removidos; dentro da janela sobrevivem; audit registra operation='purge'.
  • Cap backstop: eviction worst-first até o cap; protegidos/+feedback/hub nunca evictam.
  • archived_at: setado na demoção; migração backfilla dos updated.
  • Idempotência: segundo run sem novos elegíveis não deleta nada.
