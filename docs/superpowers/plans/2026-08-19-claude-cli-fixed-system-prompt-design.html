Design document · 2026-08-19

Fixed system prompt in ClaudeCliAdapter

Every headless `claude -p` call currently wastes tokens on dynamic system-prompt data that invalidates the prompt cache. This design fixes it to a static constant, eliminating ~7k cache-write tokens per call — a 3.0× cost reduction.
Status: approved Scope: claude_cli_adapter.py + tests

Problem: the cache-write tax

Every headless call from ClaudeCliAdapter (maintenance jobs and ingest) currently makes a claude -p request with the default Claude Code system prompt. That prompt injects dynamic data — current working directory, git status, environment variables — which changes on every invocation, invalidating the prompt-cache prefix.

The result: a ~7.7k token cache_write charge on every single call.

Measurement: paired A/B test

Test date: 2026-08-19 | identical argv, same --json-schema and hardened --settings | steady-state baseline (first call excluded):

Configuration cache_write (tokens) Cost per call
Today (default system prompt) 7,726 every call $0.0182
Fixed --system-prompt 110 $0.0061

Result: 3.0× cheaper per call. Total context stays nearly flat (~27k vs ~25.7k) — the change is prefix stability. Since cache_write bills at 1.25× and cache_read at 0.1×, prefix reuse compounds the savings.

Compatibility verified on claude CLI 2.1.235: --system-prompt + --json-schema + hardened --settings returns schema-conformant JSON, exit 0. The flag --exclude-dynamic-system-prompt-sections adds nothing over --system-prompt alone.

Decision: module-level constant

Pass a fixed system prompt on every call via a module-level constant. No constructor parameter, no Settings knob, no environment variable — any mutable source reintroduces prefix variability and incurs the full cache_write again.

The constant

_SYSTEM_PROMPT = (
    "You are a text-analysis engine used by Ormah's background memory jobs. "
    "Follow the instructions in the user message exactly. Output only the "
    "requested result — when a JSON schema is provided, reply with JSON that "
    "conforms to it and nothing else."
)

Declared next to _HARDENED_SETTINGS with a comment citing the measurement (7,726 → 110 cache_write, 3.0× cost savings).

The prompt is intentionally task-neutral: both callers (pair_batch and ingest extraction) pass all task context in the user message, so the system prompt does not influence judgment.

argv change

Append "--system-prompt", _SYSTEM_PROMPT unconditionally to the existing argv block (currently claude_cli_adapter.py:207-215).

Usage logging for observability

The adapter currently discards usage and total_cost_usd from the CLI JSON envelope, so cost can only be tracked with an external shim. As part of this change, emit one best-effort logger.info per call after the envelope is parsed, with these fields from envelope["usage"] / envelope["total_cost_usd"]:

  • input (tokens)
  • output (tokens)
  • cache_read (tokens)
  • cache_write (tokens)
  • cost_usd

Error handling: envelope without usage → no usage line, no exception. Every existing failure path of generate() stays byte-for-byte unchanged.

Tests: TDD — red before green

  1. test_argv_pins_fixed_system_prompt — assert the built argv contains the adjacent pair --system-prompt, _SYSTEM_PROMPT (same style as the existing test_argv_pins_model_and_json_output).
  2. test_usage_logged_from_envelope — an envelope carrying usage + total_cost_usd produces exactly one logger.info call with all five fields (verified via caplog).
  3. test_missing_usage_never_breaks_parse — an envelope without usage returns a normal result, logs nothing, and raises no exception.

The existing test_real_claude_* integration tests exercise the new flag automatically when run with -m integration.

Verification plan

Heavy assumptions first:

1. Quality A/B gate — the zero-quality-trade-off claim is currently assumed

Drift in output quality is invisible without measurement. Use the eval framework to confirm:

  1. Mine 100 pairs from the production store: 
    python -m eval.maintenance.cli mine --db ~/.local/share/ormah/memory/index.db -n 100
    (read-only, path from Settings().db_path on this machine; never commit or share the output pairs.jsonl — it is sensitive)
  2. Run on current code with run --mode single → save before.json
  3. Apply this change; run run --mode single again → save after.json
  4. Compare: report --single before.json --batched after.json
  5. If the gate fails → stop investigation before any merge
2. Unit tests and lint

make test (all green) + make lint (no violations)

3. Live cache_write baseline

Restart the daemon. The first auto_linker run after boot doubles as the live measurement: read cache_write from the new usage log and compare against the 7,726 token baseline.

Expected steady-state: ~110 tokens per call (after the first call is excluded).

Out of scope

  • ORMAH_MAINTENANCE_PAIRS_PER_CALL` (K) stays at 10 — deferred by André (2026-08-19) to a future change behind the per-job A/B eval gate (Council C3, issue #87). Not included here because batching contaminates the system-prompt measurement and carries a real judgment-quality trade-off.
  • No persistence of usage data — log line only, no metrics store.
  • The external shim (/tmp/claude-501/claude-usage-shim.sh) is retired, not installed.

Known risk: flag rename

--system-prompt is verified on claude CLI 2.1.235. A future rename of the flag fails loud, not silent: claude -p exits non-zero and triggers the existing logger.warning("claude -p exited …") + None return, which will be visible in the daemon log.
