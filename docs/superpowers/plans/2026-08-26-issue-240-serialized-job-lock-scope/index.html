Issue #240 — scope L_mem to the apply step: implementation plan

Overview
Background jobs stop holding L_mem for a whole run; they hold it only around each apply step, guarded by a restore epoch that aborts the run if a full graph restore lands mid-run.

Background and goal

Spec: docs/superpowers/specs/2026-08-26-issue-240-serialized-job-lock-scope-design.md (read sections 2, 3, and 5 before Task 1).

Architecture: MemoryEngine gains a monotonic _restore_epoch, bumped inside reload_restored_graph (already exclusive under L_mem), and a memory_operation_at(epoch) context manager that takes L_mem and raises RestoredUnderfoot if the epoch moved. background/memory_lock.py loses serialized_memory_job and gains RestoredUnderfoot plus restore_aware_job, a decorator that reads the epoch on entry, passes it to the job as its second positional argument, and swallows RestoredUnderfoot so the run ends cleanly instead of raising into APScheduler. Each of the seven jobs wraps its own apply steps.

Tech Stack: Python 3.11+, pytest (asyncio_mode = auto), threading.RLock, SQLite via ormah.index.db.Database.

Global constraints

  • Island: work happens in /Users/andre/Documents/GitHub/Tools/ormah-wt-240 on branch fix/240-serialized-job-lock-scope, cut from upstream/main. Never cd elsewhere.
  • Planning artifacts: the spec and this plan live on local-main in the main checkout, never on the island. The pre-push hook is fail-closed and ^docs/superpowers/ is in its PROTECTED allowlist.
  • Acquisition order is always L_mem → L_db. No apply step may take L_mem inside an open db.transaction(); that inversion is what #207 fixed. Task 10 adds the net that keeps it closed.
  • Abort, do not skip. On epoch change the whole snapshot is stale: let RestoredUnderfoot propagate out of the job body. Never catch it per-item.
  • index_updater and the FileStore scan are out of scope (spec §4). Do not touch src/ormah/index/builder.py.
  • No new try/except Exception around an apply step that would swallow RestoredUnderfoot. Several jobs already wrap their whole body in except Exception — Task 1 makes RestoredUnderfoot survive that by having restore_aware_job handle it outside, so each job must re-raise it from any inner handler it passes through.

Task 2: LockProbe — the depth-0 acquisition counter

Deliverables

Depth-0 acquisition counter for testing

Files:

  • Create: tests/test_background/lock_probe.py
  • Test: tests/test_background/test_lock_probe.py (create)

Key interfaces: LockProbe(real_lock), install_probe(engine) → LockProbe.

Why depth-0: L_mem is an RLock. A job that takes it and then calls engine.remember() — itself @_serialized_memory_operation — re-enters the same lock. Counting raw __enter__ calls yields the wrong number, hiding the bug. Only a 0→1 transition is a real acquisition.

Task 3: run_decay — per-node apply step and tier revalidation

Key pattern: Whole-run exclusion was the only thing stopping decay from demoting a node promoted after decay snapshotted it. This task closes that window by re-reading the row inside the apply step. Task 5: run_auto_linker — the 25-minute symptom

Deliverables

run_auto_linker that releases L_mem across the LLM call

Files:

  • Modify: src/ormah/background/auto_linker.py
  • Test: tests/test_background/test_auto_linker.py (append)

What the tests measure: The measured symptom is temporal; the cause is structural.

  1. The lock is not held across the LLM call. With 3 pairs, today the fake LLM is called 3 times, each recording lock_held=True, on 1 depth-0 acquisition. After: 3 calls with lock_held=False, and one acquisition per applied edge.
  2. Foreground progress: The fake LLM blocks; a foreground thread runs engine.remember() and must finish while the job is parked in the LLM. Today it hangs; after it passes deterministically.

run_auto_linker wraps its body in try/except Exception — add the re-raise.

Task 6: run_conflict_detection

Deliverables

Per-edge and per-node apply steps

Files:

  • Modify: src/ormah/background/conflict_detector.py
  • Test: tests/test_background/test_conflict_detector.py (append)

Shape of this job: Candidate discovery is read-only and stays unlocked. Two write regions separated by the LLM loop: per-pair edge insert, then after the loop, the markdown flush over dirty_nodes. Both get their own memory_operation_at(epoch). The markdown flush takes one acquisition per node, not one for the whole dict.

Important: The body is wrapped in try/except Exception — add the re-raise. The inner try/except Exception catches per-node markdown failures; it must not swallow RestoredUnderfoot, so the guard goes outside that try.

Task 7: run_duplicate_detection

Deliverables

Per-merge and per-proposal apply steps

Files:

  • Modify: src/ormah/background/duplicate_merger.py
  • Test: tests/test_background/test_duplicate_merger.py (append)

Shape of this job: Two write regions per pair, mutually exclusive by score: auto-merge (engine.execute_merge(...)) and proposal insert. The guard must wrap auto-merge anyway — the decorator gives per-call atomicity, not the epoch check, and the RLock makes nesting free.

Important: The try/except Exception catching auto-merge failures must not swallow RestoredUnderfoot — put the guard outside it. The outer body-wide try/except Exception gets the re-raise.

Task 8: run_consolidation

Deliverables

One cluster's consolidation as a single atomic apply step

Files:

  • Modify: src/ormah/background/consolidator.py
  • Modify: src/ormah/engine/memory_engine.py
  • Test: tests/test_background/test_consolidator.py (append)

Shape of this job: _apply_consolidation is one logical unit — new node, identity edge transfer, derived_from edges, demote-to-archival — spread across several already-per-call-locked engine methods. Wrap the whole function body in one memory_operation_at(epoch) when a job epoch is supplied. One cluster's consolidation must be atomic with respect to a restore, not split across acquisitions.

Important: run_consolidation's per-cluster loop wraps each _consolidate_cluster call in try/except Exception to keep one bad cluster from aborting others — that handler must not swallow RestoredUnderfoot, since an abort means the whole run's candidate list is stale.

Task 9: split ingest_conversation extract from apply

Deliverables

Unlocked extraction with revalidated dedup

Files:

  • Modify: src/ormah/engine/memory_engine.py
  • Test: tests/test_engine/test_ingest.py (append)

Why this one is different: Not a scheduled background job — it is called synchronously from the API/CLI. Uses MemoryEngine.memory_operation() (already exists), not memory_operation_at. The fix is narrower: stop locking the extraction (the LLM call) while still locking each apply correctly.

The debt this creates: _is_duplicate_memory reads outside the lock now. Two concurrent ingest_conversation calls extracting overlapping content can both read "not a duplicate" before either writes. Revalidate inside the same acquisition that calls remember.

Task 11: pay the revalidation debt in the three remaining jobs

Deliverables

Revalidation in consolidator, auto_cluster, duplicate_merger

Files:

  • Modify: src/ormah/background/consolidator.py — _apply_consolidation's demote loop
  • Modify: src/ormah/background/auto_cluster.py — the per-node apply step
  • Modify: src/ormah/background/duplicate_merger.py — the auto-merge apply step
  • Test: append to all three test files

Why this exists: Spec §5 named decay's tier revalidation as a debt created by removing whole-run exclusion. Task 3 paid it. The final whole-branch review found the identical shape unguarded in three other jobs. Each needs the same treatment: inside the apply step, re-read what the write depends on; if it changed, skip this item and let the next run reprocess it.

The three windows:

Job What is stale Concrete failure
Consolidator the cluster's node_ids, snapshotted before the LLM call node N is snapshotted as working; the user promotes it to core during the LLM call; the apply step demotes it to archival, silently undoing the promotion
Auto-cluster "this node has no space", from the candidate query user assigns a space between the query and the apply step; the apply step overwrites it
Duplicate merger both nodes' content, which the LLM wrote merged_content from user edits the kept node during the LLM call; execute_merge overwrites it with merged text derived from the pre-edit content

Important: Skip the item, do not abort the run. One node changing invalidates that node, not the whole run. Requires Tasks 1–10 all complete and committed.
