A arquitetura do fix

Duas camadas independentes. Elas falham separadamente, de propósito: a primeira mata o gatilho, a segunda é um backstop estrutural para a classe inteira do bug.

Camada 1 — abandono explícito no _ingest_session

should_rewind dispara quando um parse a partir do cursor guardado vê um órfão inicial e não faz progresso. A recuperação re-parseia do zero: uma probe sem cap decide se há algo recuperável, mas o drain com cap (max_bytes=flush_bytes) é o que era commitado. Quando o arquivo é maior que flush_bytes, o safe_end_offset do drain cai abaixo do cursor original — o commit move o cursor para trás, ticks posteriores sobem de volta, o órfão dispara de novo. Loop permanente.

O gate de progresso só permite a recuperação quando a fatia do drain ultrapassa o cursor original. Caso contrário a cauda é abandonada explicitamente: o cursor avança, a faixa de bytes vai duravelmente para skipped_slices com reason=orphan_above_cap, e o job completa — zero chamadas de LLM.

Por que não um NO_PROGRESS simples. Council R1, ambos os peers, verificado em código: _run_job converteria um NO_PROGRESS com cauda idle insegura num bump de cursor até o EOF via _idle_with_unsafe_tail/_mark_frozen_prefix_consumed — o cursor avançaria por efeito colateral, sem nenhum registro de perda. O abandono explícito troca um efeito colateral invisível por uma decisão auditável.

Camada 2 — invariante monotônica no _commit_state

end_offset nunca pode decrescer, salvo quando o chamador passa allow_rewind=True. Três propriedades são carga estrutural, cada uma vinda de um round de council:

PropriedadeOrigemO que quebraria sem ela
compare-and-clamp dentro do state_lockR1, Codexuma leitura stale fora do lock deixa dois writers intercalarem 200-depois-150 e persistirem a retração
clampa só o campo end_offset, nunca a entrycouncil-pr I1descartar a entry perderia extract_fail_count e a trilha de quarentena
persist-then-publishR2, Codexum _save_state que falha deixaria o dict em memória reivindicando um cursor que o disco nunca recebeu

O caminho de shrink (prev_offset > size) é a única retração legítima — sem essa escotilha, o clamp congelaria o cursor acima do EOF e o run_session_reconcile tiraria o arquivo da varredura para sempre.

A invariante que torna o trade barato

Estabelecida na revisão final do branch, rastreando o parser.py: _would_overshoot exige um prefixo seguro não-vazio, então o cap de bytes nunca pode suprimir o primeiro fechamento. Logo, se existisse qualquer turno de usuário seguido de um assistant terminal acima do cursor, o parse já teria fechado ali e o should_rewind não poderia ter disparado.

A faixa abandonada nunca pode conter um par user↔assistant completo — é exatamente a cauda da única resposta aberta. Por isso a perda real é ~1 KB por looper, não uma conversa inteira.

As três tasks

1 Abandono explícito da recuperação above-cap

Arquivos: src/ormah/background/session_watcher.py (bloco de orphan-recovery dentro de _ingest_session) · tests/test_background/test_session_watcher.py (classe nova TestAboveCapOrphanRecovery + um helper de fixture no nível do módulo).

Produz: o helper _write_orphan_tail_jsonl(path, pairs, pad), reusado verbatim pelos testes da Task 2, e a chave de estado skipped_slices[].reason == "orphan_above_cap" — a trilha durável que o backfill diferido vai consumir.

Onze steps, TDD: helper de fixture → teste de loop que nasce vermelho (a monotonicidade quebra num ciclo de período 7) → teste-guarda de arquivo pequeno (o one-shot documentado do #154 precisa sobreviver) → implementação → teste no nível do worker, pelo caminho real spool → _run_job → teste de composição com cauda unclosed → módulo inteiro → commit.

Três constraints estruturais da implementação (council R2/R3)
  • O alvo do abandono é o safe_end_offset da probe — fronteira de turno FECHADO, alinhada a linha, respeitando o teto do stop_offset. Nem min(size, boundary) cru (pode bissectar um record escrito em voo) nem o end_offset da probe (o f.tell() pode ultrapassar o teto num record que atravessa a fronteira, e avança sobre JSON malformado no fim).
  • O commit tem de viver FORA do try largo de parse: o except Exception dele retorna NO_PROGRESS, então um OSError do _save_state se disfarçaria de falha de parse e rotearia um transcript válido para o tratamento de frozen-prefix/dead-letter. Dentro do try, só DECIDE.
  • Bytes acima do safe_end_offset ficam não-consumidos de propósito — são a classe in-flight-forever que o ADR-0003 já se recusa a ingerir.
2 Backstop monotônico no _commit_state

Arquivos: session_watcher.py (_commit_state, flag de shrink, keying da falha, três call-sites) · test_session_watcher.py (estende a classe da Task 1 + uma classe unitária TestCommitStateMonotonic).

Produz: _commit_state(..., *, allow_rewind: bool = False) — o keyword é o seam que o backfill do ADR-0004 vai usar.

A auditoria de 2026-07-30 encontrou que 3 dos 4 call-sites do _commit_state podiam escrever um end_offset menor que o guardado: o caminho de rewind zera o prev_offset, então o caminho de falha de extração literalmente commitava end_offset=0, e os caminhos de quarentena e happy path comparavam contra 0 em vez de contra o cursor guardado. A Task 1 remove o gatilho do loop; esta task faz a camada de estado rejeitar a classe inteira.

Duas revisões do council R1 incorporadas
  • (Codex) O compare-and-clamp tem de viver DENTRO da seção crítica do state_lock. Writers cross-processo continuam desprotegidos — threading.Lock não atravessa processos. É a limitação #150-class pré-existente, documentada na docstring, fora de escopo aqui.
  • (Cursor) O contador de falhas tem de ser chaveado no cursor durável pré-rewind, não no prev_offset zerado transitório — senão uma entry clampada carrega end_offset=orphan_start com extract_fail_offset=0, um par inconsistente. Um local fail_key_offset conserta o check e a escrita.
3 Guard de startup do servidor

Arquivos: src/ormah/config.py (função nova validate_llm_runtime_config) · src/ormah/main.py (chamada no startup) · tests/test_config.py.

ORMAH_LLM_PROVIDER=ollama sem ORMAH_LLM_MODEL manda silenciosamente o id de modelo default da Anthropic para o Ollama. Todo job de manutenção — auto_linker, duplicate_merger, conflict_detector, consolidator, juiz de feedback — leva um 404 por chamada, para sempre, com apenas um WARNING por chamada. Essa combinação exata manteve o pipeline de manutenção inteiro morto (143 × 404 só em 2026-07-30).

Deliberadamente NÃO é um model_validator do pydantic (council C2, codex — supersede a abordagem dos rounds R3/C1). O config.py constrói um singleton global Settings() ansioso no import, e o ormah setup importa através dele — um model validator lançaria ValidationError justamente para os usuários que carregam o par legado ruim, bloqueando o próprio caminho de reparo deles (o ormah setup --update roda sob o set -e do instalador, então upgrades também abortariam). Um guard de startup do servidor dá o mesmo fail-fast onde importa.

Council C3 (cursor) achou o seam errado no v6: o Beta sobe via ormah server start → uvicorn.run("ormah.main:app") e nunca executa o bloco __main__ do main.py — um guard ali passaria no smoke e não protegeria nada. A chamada vive no caminho de import do app, no lifespan().

Contrato que o backfill precisa honrar (revisão final): o bloco abandonado é, por definição, não-parseável a partir do próprio start — é a cauda de uma resposta ainda aberta. Então o backfill tem de re-parsear a partir do offset 0 para reemparelhá-lo com seu prompt, e tem de verificar o source_hash do registro contra o arquivo atual antes de replicar qualquer coisa. Um reset de shrink pode deixar skipped_slices descrevendo um arquivo que não existe mais; o hash por registro é o discriminador de carga, não decoração.
