Tornar o backfill cancelável colapsa a classe inteira de bugs — não remenda sintoma a sintoma.

A decisão e a raiz

Goal: fechar o cluster de lifecycle do round 2 do council-pr — CRA (use-after-close de SQLite no shutdown), CRB (singleton não-atômico), CRC (run-all não persiste no health) e IA (thread órfã bloqueia o fallback do engine novo).

A raiz comum: o daemon executava run_embedding_backfill de forma não-interrompível, então parar/desligar corria com ele. A tentativa anterior (CR1) preservava o handle no timeout do join — trocou uma race por duas. Após 3 subagents sonnet analisarem independentemente (2 recomendaram A, 1 recomendou eliminar o daemon), a escolha foi Opção A simplificada: o daemon fica (council I1 exige recuperação independente do scheduler), mas o backfill vira cooperativamente cancelável.

Por que o daemon fica O fallback só roda quando start_scheduler lança exceção (main.py:151-158) — estado de falha de config raro. O problema original do #32 já está resolvido pelo job do scheduler; isto endurece o caminho degradado sem reabrir council I1 (o que a Opção C faria).

Shutdown seguro

O ponto técnico que fecha CRA de verdade: a checagem do stop_event acontece antes de cada acesso ao DB (cada upsert_batch/wal_checkpoint), não só no loop de encode. Quando _stop_backfill_fallback retorna, a thread já liberou o DB — só então engine.shutdown() fecha a conexão.

Modo schema Se o passo schema for interrompido, não avançar o embedding_schema_version — senão um reprocesso parcial parece completo e nós não-reprocessados ficam invisíveis aos delta runs. Guard: if mode == "schema" and not interrupted.
